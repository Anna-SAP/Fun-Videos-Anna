## 过程中遇到的情况

| # | 情况 | 怎么处理的 |
|---|---|---|
| 1 | 没有图片生成 API，也没有 OpenAI 的转写 API | 画面全部由程序计算；识别和对齐全部用本机 CPU 上的模型 |
| 2 | 结构分析脚本给出 70.8 BPM，和"主歌每句 2.83 秒"对不上 | 三连音 hi-hat 把自相关带偏了（85 × 5/6）。改用伴奏起音做梳状拟合，得到 84.99 BPM；小节线用"鼓第一次进来"的位置定 |
| 3 | 歌词单上写的"鼓抽掉""鼓全停"在这个生成版本里没有发生 | 以量出来的为准：段落的呼吸改由镜头距离来做（走廊远景 / 门前近景），不假装音乐停了 |
| 4 | Whisper 强制对齐把一个词的几个字挤在同一瞬间 | 加了第二个、原理不同的对齐器（MMS 的 CTC 对齐，汉字转拼音）。它字距均匀，但句首句尾会漂、有合唱时失灵。两者一致处当锚点，各取所长（见 storyboard 第 4 节） |
| 5 | 第三段主歌前两句，两个对齐器都把第二句的开头放进了第一句里 | 自检时发现相邻两句时间重叠，对着频谱图手工重排 |
| 6 | 实际演唱和歌词单有四处出入（Drop 的口号唱了三遍、有两个短句没唱等） | 没有停下来问：按"唱了什么就在唱的那一刻出现什么"处理，交付时逐条列出 |

## 拆解

1. **"准确"被拆成了两个可以检查的条件**：文字和原文一致；时机和演唱对得上。前者用断言保证（排版模块逐行核对"屏幕上的字符 = 歌词单的字符"）；后者靠两个对齐器加频谱图。这样写比"歌词要准"好验收得多。
2. **"不要只是把字幕叠在背景上"** 排除了最省事的做法，逼出一条规则：字是门上透出来的光。
3. **把段落标签和编曲备注说明成"提示，不是唱词"**，省掉了一次确认：它们没有上屏，但决定了各段的字体、颜色和镜头。
4. **歌词直接贴在提示词里**（上一支 LED 墙是从对话链接里取，取不到）。这次歌词来源没有任何周折。
